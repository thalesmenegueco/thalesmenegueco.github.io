PROJECT: Add a Timeline/Gantt View to an Existing Angular Project Manager

ROLE

You are an AI coding agent working inside an existing Angular and TypeScript project manager application.

Your task is to implement a new Timeline/Gantt visualization for existing projects and tasks.

The application already has:

- An established visual identity
- Existing project and task data models
- Existing services, stores, facades, or state management
- Existing navigation and detail views
- Existing styling conventions and design tokens

Do not redesign the application. Do not replace existing models unnecessarily. Do not introduce a new visual language unless the existing project has no equivalent pattern.

PRIMARY OBJECTIVE

Build a read-only timeline view that helps users understand:

1. Which projects and tasks exist
2. When each project or task starts and ends
3. Which tasks depend on other tasks
4. What must finish before another item can begin
5. Which items belong to the same project
6. Which predecessor chain leads to the currently selected item

The first version should prioritize clarity, correctness, maintainability, accessibility, and low coupling with the existing application.

Do not implement a complete project scheduling system in the first version.

VERSION 1 SCOPE

Include:

- Projects displayed as groups or summary rows
- Tasks displayed as timeline rows
- Start and end dates
- Task duration bars
- Project summary bars when dates are available
- Horizontal scrolling
- Timeline date headers
- Grid lines
- Visible dependency connectors
- Arrowheads showing dependency direction
- Task selection
- Keyboard-accessible task selection
- Highlighting of direct predecessors
- Subtle highlighting of indirect predecessors
- Existing task/project detail navigation through an output or callback
- Loading state
- Empty state
- Validation-error state
- Invalid data handling without breaking the entire view
- Support for approximately 100 tasks per project without virtualization

Do not include in version 1:

- Drag-and-drop date editing
- Resizing task bars
- Inline editing
- Visual creation or deletion of dependencies
- Automatic task rescheduling
- Critical path analysis
- Slack or float calculations
- Resource allocation
- Workday calendars
- Holidays
- Multiple dependency types
- Lead or lag values
- Complex zoom controls
- Virtual scrolling
- A third-party Gantt library unless the existing project already uses one and it is clearly appropriate

DEFAULT DEPENDENCY TYPE

Use finish-to-start dependencies for version 1.

Meaning:

- The predecessor must finish before the successor begins.
- The connector starts at the right side of the predecessor bar.
- The connector ends at the left side of the successor bar.

NORMALIZED DATA CONTRACT

Adjust names to match the project’s conventions, but preserve this conceptual shape:

type TimelineItemKind = 'project' | 'task';

interface TimelineDependency {
  readonly predecessorId: string;
  readonly type: 'finish-to-start';
}

interface TimelineItem {
  readonly id: string;
  readonly kind: TimelineItemKind;
  readonly parentId?: string;
  readonly label: string;
  readonly start: string;
  readonly end: string;
  readonly status?: string;
  readonly progress?: number;
  readonly colorToken?: string;
  readonly dependencies: readonly TimelineDependency[];
}

interface TimelineViewConfig {
  readonly scale: 'day' | 'week' | 'month';
  readonly rowHeight: number;
  readonly barHeight: number;
  readonly unitWidth: number;
  readonly showToday: boolean;
}

interface TimelineIssue {
  readonly code: string;
  readonly itemId?: string;
  readonly relatedItemId?: string;
  readonly message: string;
  readonly severity: 'warning' | 'error';
}

The normalized model must be immutable from the perspective of the renderer.

Do not mutate input project or task objects.

DATE RULES

Choose one internal date representation and document it.

Recommended internal behavior:

- Convert source dates once in the adapter.
- Use calendar-day indexes in the pure engine.
- Use a half-open interval internally:
  [startDay, endDayExclusive)

If the existing domain treats the end date as inclusive, convert it once in the adapter.

Do not silently alter or persist the normalized dates back into the domain model.

Validate:

- Invalid date strings
- Missing dates
- End date before start date
- Zero-duration tasks
- Date boundaries across months
- Date boundaries across years
- Leap-year dates
- Timezone-related inconsistencies

Never allow these values into geometry calculations:

- NaN
- Infinity
- Negative widths
- Negative heights
- Undefined x positions
- Undefined row indexes

For zero-duration items, preserve the real date but render a milestone or minimum-width visual marker.

TIMELINE RANGE

Calculate the global timeline range from valid items.

Recommended process:

1. Convert every valid item date to an integer day index.
2. Find the minimum start day.
3. Find the maximum end-exclusive day.
4. Add visual padding around the range if useful.
5. Generate all headers and grid lines from this same range.
6. Use the same coordinate conversion for headers, bars, grid lines, and connectors.

Use a single coordinate function conceptually equivalent to:

x = (dayIndex - rangeStart) * unitWidth

Use a single width function conceptually equivalent to:

width = (endDayExclusive - startDay) * unitWidth

The exact function names are not important. Consistency is important.

LAYOUT RULES

Flatten hierarchical items in a predictable order.

Recommended order:

- Project
- Visible child tasks
- Next project
- Its visible child tasks

Store a row index for each item ID.

Each item should appear only once.

Projects with explicit dates should use those dates.

If projects do not have explicit dates, only derive summary dates from children if this is compatible with the existing product semantics.

Derived project dates must:

- Be marked internally as derived
- Not be persisted back into the domain accidentally
- Be covered by tests

Return a layout result containing the calculated data needed by the renderer, such as:

- Timeline range
- Header units
- Rows
- Bars
- Row indexes
- Dependency edges
- Connector paths
- Today marker position
- Validation issues
- Content width
- Content height

All layout output must be deterministic for the same input.

DEPENDENCY GRAPH

Represent each dependency as:

predecessorId -> successorId

Validate:

- Missing predecessor
- Missing successor
- Duplicate dependency
- Self-dependency
- Cycles
- Unsupported dependency type

A dependency problem should not crash the whole timeline.

For invalid edges:

- Produce a validation issue
- Do not generate a connector path for that edge
- Continue rendering valid items and valid edges

Use a reverse adjacency map for predecessor traversal.

When a task is selected:

- Highlight direct predecessors strongly
- Highlight indirect ancestors subtly
- Reduce the prominence of unrelated dependency edges
- Avoid infinite traversal by using a visited set

CONNECTOR ROUTING

Use SVG paths for dependency connectors.

The first version only needs predictable orthogonal routing.

Recommended routing:

1. Start at the right edge of the predecessor bar.
2. Move horizontally.
3. Move vertically through a calculated routing lane.
4. Move horizontally toward the successor.
5. End at the left edge of the successor bar.
6. Add an arrowhead pointing toward the successor.

Handle:

- Predecessor before successor
- Successor before predecessor
- Overlapping bars
- Same-row relationships
- Multiple edges using the same lane
- Several edges between nearby rows

Use deterministic lane assignment.

Keep connectors behind the task bars.

Set connector pointer events to none in version 1 so connectors do not prevent task-bar interaction.

The connector layer is visual support. The DOM labels and buttons remain the primary interactive and semantic representation.
